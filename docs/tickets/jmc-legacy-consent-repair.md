# JMC legacy event-contact consent repair

The 6 November 2026 JMC event used a required event-contact agreement before separate optional follow-up/newsletter choices were introduced on 8 November. The added boolean defaulted pre-existing records to false, hiding that original agreement from the school-mail audience. The live cohort contains 127 RSVP addresses and three programme-only addresses; 33 addresses also have differing names across source records.

Migration `2026_11_18_140000_restore_jmc_event_follow_up_consent` records a separate nullable `legacy_event_follow_up` permission for the Jose Maria College Foundation, Inc. partnership-classified school visit (slug `jmc`) on 6 November at 08:30 Asia/Manila. Records must have both registration and original consent before 8 November at 00:00 Philippine time. Cancelled RSVPs, later audited withdrawals and subsequently corrected identities are excluded. Candidate records are locked before audit evidence is read, matching the staff editor’s lock order. Original consent timestamps, submission fingerprints, optional study-tip/adviser and newsletter preferences, verification and applicant links are preserved. The legacy flag is used only by the school-visit follow-up audience; it does not preselect optional email subscriptions. Staff can withdraw that event permission in Edit answers. An explicit event-specific No overrides broader follow-up choices. Identity corrections remove legacy applicability, so the previous identity’s agreement cannot be reactivated through the editor.

Each changed table/visit has an `education.jmc.legacy_follow_up_restored` activity record listing the affected record IDs, original agreement source and before/after permission. No mailing, outreach receipt, subscription, or job is created. Existing unsubscribe, bounce, address/identity and conflicting-source checks still apply.

The migration is idempotent. Application rollback retains the nullable mapping columns and their audited choices so an explicit withdrawal cannot become indistinguishable from an unmapped record; old application code ignores these columns. Original consent and optional choices remain unchanged. Reapplying the repair checks later recorded withdrawals again; it does not reinstate permission after an audited opt-out.

School Mail now shows the individual RSVP/programme names behind an identity exclusion so staff can review the actual evidence. Displaying those names does not change identity matching or create applicant links.

## Live metadata and name review

The public visit catalogue identifies the JMC event with slug `jmc`, kind `partnership`, date `2026-11-06`, time `08:30`, and timezone `Asia/Manila`. The initial repair's school-kind predicate skipped that live record. Forward migration `2026_11_18_150000_replay_jmc_event_consent_mapping` reruns the idempotent repair using the verified slug and partnership metadata. Tests exercise that forward replay against the same event shape.

The 33 reviewed groups contain 33 RSVP sources and 39 programme-registration sources. Most differences are omitted middle initials/additional given names or explicit surname-first formatting. Two groups had differing/missing surnames. The requester confirmed both canonical full names from the RSVP sources. The forward migration corrects those two programme-registration name fields only, guarded by exact source IDs, visit, matching email and the captured source-name fingerprint. The original RSVP names, submission fingerprints, other contact fields, client accounts and optional preferences remain unchanged; corrections have a separate audit trail. Reconciliation itself does not rewrite stored names.

For event follow-ups only, a non-exact name can be reconciled when every source has recognised legacy event permission and the same valid phone number after the existing E.164 normalizer. Full first given name and surname must match; additional names may be omitted, and an initial must agree with a present complete name. All source pairs are compared so a short name cannot hide conflicting complete names. Different surnames, conflicting given names/initials, generation suffixes, different/missing phones, non-legacy groups and newsletter mailings retain the stricter exclusion. Source names and whether contact numbers match remain visible for unresolved groups. Surname-first legacy RSVP names are personalised in given-name order without changing their original answers.
