# TKT-UA9PPC — Engagement deletion feedback

Nova reports that a Sent engagement remains after Delete and displays “Could not delete the documents.” The existing button replaces every server validation explanation with that generic text. The backend deliberately rejects whole-pack deletion when an invoice is linked to a Finance receivable or recorded payment; it validates the complete selected pack before removing any files. That is a reproducible matching condition, not confirmation that Nova’s specific production record has that linkage.

Keep the existing deletion and financial-retention rules. Display the actual server error both beside the selected row and in the toast, and explain the Finance restriction before confirmation. Guard the confirmation and request against duplicate clicks; cancellation sends no request and a failed attempt can be retried. Successful deletion continues to use the existing server-refreshed list. No endpoint, roles, ownership policy, storage rule, invoice calculation or schema is changed.

Synthetic backend tests exercise an Immigration manager deleting a colleague’s unlinked draft/sent pack, isolation from another pack, protected issued Finance invoices and client/agent denial. Actual React tests cover confirmation/cancellation, exact Finance feedback, row retention, retry, legacy/selected pack targeting and removal after a server list refresh. Existing Engagement search/signature and payment/workflow regressions remain part of verification.

This is a feedback correction, not permission to erase issued invoices or payment evidence. Ticket closure requires the affected record’s actual server reason and requester acceptance. If the business need is to remove a Finance-linked Sent pack from the workspace while retaining its history, obtain an explicit archive/workspace-removal decision. If the invoice was issued incorrectly, Finance must review cancellation/correction; do not bypass the retention guard or delete financial history to make the button appear successful.
