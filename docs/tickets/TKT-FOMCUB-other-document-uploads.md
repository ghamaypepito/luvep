# TKT-FOMCUB - Append supporting files under Other

## Findings
Originally reviewed main 17c2d918 on 17 November 2026; rebased and rechecked against main 550fe05a on 19 November 2026. No equivalent direct Other-upload addition was found. The screenshot's 0/3 header is the approved/total row count, not a three-slot capacity. Existing unmatched document rows have no checklist key; UploadSlot intentionally cannot upload against them. Request documents can create ad-hoc client requests, but can email the client and is not the requested direct staff upload path. Existing checklist/request uploads already accept up to 10 files per batch with the shared 50 MB document policy; no three-file case-wide storage cap was found in these paths. Jonathan's actual record/upload response was not inspected, so this diagnosis does not exclude a separate storage/server failure on his record.

## Resolution
Add Upload other documents to the Immigration case Documents tab, separate from Request documents. Authorized active Immigration staff, managers, advisers and admins can append PDF/image/Word/Excel files without preallocating slots or replacing existing files. Upload another batch as needed; up to 10 files per request and the existing shared 50 MB/file limit remain. Server/PHP request limits and available disk capacity still apply.

The new dedicated case endpoint checks actual staff role and canonical case membership, including legacy handoffs. Extra portal grants do not turn other roles into Immigration staff. Soft-deleted/archived records are excluded by normal model scope. Files are stored privately under the same case document directory; new LeadDocuments have null checklist/request keys, source upload and status Submitted. No client request/email is sent, no approval/payment status is assigned, no migration or existing file rewrite occurs. New rows appear in Other (no checklist match). After success, the view clears the status filter and expands Other. UI prevents overlapping submissions and shows validation errors/retry controls. Duplicate filenames remain separate files.

Metadata insertion is transactional. A failed batch rolls back its new rows and removes only its new stored files. Findings refresh is queued after upload completion; queue dispatch failure is logged without deleting committed files. Existing shared upload routes, request workflow, case catalogue, invoice/payment controls, review/status logic and other portal screens are unchanged.
